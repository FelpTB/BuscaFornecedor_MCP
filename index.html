01 · Scrape em escala

Scrape em escala

Coletar evidência web em massa — main page e subpáginas — antes do enriquecimento por LLM.

Objetivo

Realizar scrape em massa de milhares de sites de empresas: baixar HTML da página principal e das subpáginas internas relevantes e persistir o conteúdo bruto no PostgreSQL (scrape_main), de forma estável e auditável.

Desafios → como o sistema responde
  • Bloqueio anti-bot / WAF → curl_cffi (fingerprint real) + proxies residenciais particionados
  • Sobrecarga e rate limit → Batch assíncrono + semáforos por provider e por URL
  • Sites heterogêneos → Timeout, 5 redirects, charset (headers/meta), pipeline em 3 etapas
  • Domínios lentos ou instáveis → Stagger, limite por domínio, circuit breaker
  • Falhas sem rastreio → error_step1..3 + reprocessamento cirúrgico
Cliente HTTP
  • curl_cffi imita Chrome/Safari — menos bloqueio por bot
  • Pool de sessões reutilizáveis; recicladas após N usos
  • Fim do batch: conexões fechadas (cleanup_after_batch)
  • Timeout configurável · até 5 redirects · charset via headers/meta

02 · Chunkenização

Chunkenização orientada ao contexto LLM

Do HTML agregado às unidades que cabem na janela do modelo — módulo app/core/chunking/

Objetivo

Transformar o texto agregado (main + subpáginas) em chunks que respeitam a janela de contexto do LLM — incluindo system prompt, formatação de chat e margem de segurança — e persistir em scraped_chunks para o profile_builder.

Desafios → como o sistema responde
  • Estourar o contexto do LLM → effective_max_tokens ≈ 14 705 (não usar só max_chunk_tokens)
  • Páginas gigantes (~40k tokens) → _split_large_page() + enforce_limit() recursivo
  • Excesso de chamadas LLM → Agrupar páginas pequenas até ~group_target_tokens (12k)
  • Ruído (menus, headers) → dedupe em escopo document
  • Contagem de tokens imprecisa → Validar chunk inteiro · fallback _split_by_chars
Entrada · agregação
  • Texto unificado do scrape com marcadores por URL
  • process_content() → SmartChunker + ChunkValidator

  • 1 chunk → 1 inferência → perfil completo
  • N chunks → merge LLM (sem alucinar campos vazios)

03 · LLM auto-hospedado

LLM auto-hospedado: custo abaixo da API comercial

Qwen2.5-14B (Phoenix fine-tuned) · SGLang no Vast.ai · profile_builder

Objetivo

Reduzir o custo do enriquecimento em escala — milhares de perfis via API comercial (GPT-4o, Claude etc.) ficam inviáveis por token; GPU própria no Vast.ai converte o gasto em GPU-hora previsível, muito menor no volume do pipeline.

Mesmo workload: 10k chunks → 10k JSONs · auto-hospedar < API gerenciada em massa
Desafios → como o sistema responde
  • API comercial cara em volume → LLM próprio · fila gpu_manager · pay-per-hour no Vast.ai
  • Volume massivo de inferências → SGLang: batching, KV cache — mais perfis por GPU-hora
  • JSON complexo inválido → Structured Outputs + json_schema — menos retries = menos custo
  • Custo e disponibilidade de GPU → Vast.ai: leilão mais barato + maior oferta de RTX vs RunPod
  • Modelo OSS fine-tuned → Qwen Phoenix no HF Hub · suporte SGLang antes do vLLM
1 · Throughput em massa
  • Gargalo: GPU util, não qualidade do modelo
  • SGLang otimiza batching + KV cache
  • Topo em benchmarks: req/s, tokens/s

Perfil ideal: classificação, extração, enriquecimento batch

2 · JSON estruturado
  • CompanyProfile aninhado (ofertas, contato…)
  • Menos JSON quebrado, campos faltando, retries
  • Grammar / schema nativo no servidor

JSON válido > texto “bonito”

3 · GPUs comerciais (RTX)
  • Otimizações OSS focadas em RTX 4090/5090, A6000
  • Clusters comuns: 2×–8× 4090 para inferência
  • Alternativa natural ao datacenter-only
4 · Modelos OSS recentes
  • Qwen / Llama / DeepSeek: suporte SGLang costuma sair primeiro
  • Exemplos oficiais dos labs priorizam SGLang
  • vLLM permanece opção se já estável
Pipeline · profile_builder
  • Loader → Processors (GPUs×15) → Savers (20)
  • Multi-chunk: merge sem alucinar campos vazios
  • API OpenAI-compatible · Prometheus
Deploy · Vast.ai
  • Custo: marketplace por leilão, pay-per-hour
  • Disponibilidade: mais oferta de placas RTX no momento da escala
  • Treino + inferência no mesmo ecossistema · sglang.launch_server

04 · Banco vetorizado

Busca híbrida: nuances, produto vs serviço e BM25

Qdrant Cloud (sa-east-1) · qdrant_busca · 5 vetores densos + BM25 esparso

Objetivo

Entregar uma busca funcional e rápida capaz de capturar as nuances mínimas da intenção do usuário — distinguir se a consulta pende para produto ou serviço, encontrar perfis para demandas específicas e usar BM25 para acertar nomes, SKUs e termos exatos que embedding denso dilui.

“cartucho HP 662XL” → produto · “consultoria SAP” → serviço · “SOS Cartuchos” → BM25
Desafios → como o sistema responde
  • Um embedding dilui sinais → 5 vetores nomeados por dimensão semântica independente
  • Query produto ≠ query serviço → Pesos em v_produto vs v_servico no POST /search
  • Nomes, siglas, códigos raros → bm25_complete_profile + bm25_query textual
  • Filtros geo / segmento → Payload (UF, cidade, indústria) antes da fusão de scores
  • Reindex e perfis esparsos → Point ID determinístico por CNPJ · fallbacks em cascata
